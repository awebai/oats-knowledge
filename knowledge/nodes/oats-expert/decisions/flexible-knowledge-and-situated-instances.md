# Decision

Accepted by the human 2026-09-19 (oats-expert as maintainer) and published as
the framework's canonical public explanation *before* further implementation.
This concept records the decision, its rationale and what it supersedes; the
public explanation carries the full theory.

# What was decided

- **A soul defines reusable expertise, boundaries and curriculum. An
  instance is a situated working continuity** — not necessarily a short task
  or one chat. Ephemeral reviewers and long-running expertise instances are
  both legitimate; duration alone never makes a new soul.
- **Four things are distinct**: skills/capabilities, accepted knowledge,
  working understanding, and ongoing state. Valuable instance context is not
  automatically shared knowledge, and harvesting accepted concepts does not
  reproduce an experienced instance's whole working picture.
- **The default routes knowledge centrally, per soul, within the adopter's
  chosen base.** It is a simple initial routing model — not permanent silos,
  and not implicit publication to an upstream soul publisher. Knowledge may
  grow, move, merge, or support a reviewed split of the specialisation.
- **Knowledge capabilities own their complete procedures, learning model and
  placement**, not merely storage under a kernel-owned judge. Other
  capabilities may offer topic or project organisation, co-located knowledge,
  multiple stores or different reading/promotion/maintenance models.
- **The kernel owns identity, lifecycle, resolution, approvals and custody** —
  never a mandatory knowledge taxonomy or learning pipeline. Mutable knowledge
  requires explicit supported write authority; co-location does not make a
  retained source or executable artifact writable.
- **Ownership routes harvests.** It is not authorship, an ACL, or a working
  soul's duty to keep the base honest directly.
- **Speciation follows evidence** of sustained reusable skill/read/work
  differences, with human acceptance of structural change. Repeated spawning
  is evidence, not a requirement — one long-running instance may expose a
  recurring specialisation; widening, merging or keeping the existing soul are
  equally valid outcomes.

# Rationale and rejected alternatives

- **A mandatory topic model** — rejected: it forces users to design a
  taxonomy before gaining basic shared learning.
- **A permanent one-soul/one-folder model** — rejected: it couples knowledge
  identity to a changing roster.
- A capability-owned model gives a simple default and deliberate evolution
  without a universal kernel mode switch, consistent with the
  [optional reference theory](/nodes/oats-expert/decisions/optional-reference-theory.md).

# Supersession and scope

Supersedes the mandatory topic-first reading of the 2026-09-16 exploration.
**Narrows** the 2026-09-13
[external custody decision](/nodes/oats-expert/decisions/external-knowledge-custody.md)
to the *default integration*: external placement is the default's choice, not
a kernel prohibition on co-located knowledge. Accepting the architecture
changed no API field, capability behaviour, binding or live writer; automatic
per-soul provisioning, co-located profiles, topic redirects, automatic
speciation and safe context cloning remain separate implementation and
acceptance work.

# Corollaries (lesson, 2026-09-19, redesign lead)

- **"Public", "in the same repository" and "writable at the current in-soul
  paths" are three independent requirements.** External-to-the-soul describes
  ownership and write path, not visibility or hosting. Conflating them makes
  a placement change look like a privacy change, or makes "keep it here" look
  like it forbids every new arrangement. Record the requirement the user
  actually stated; the one that usually binds is the third, because tooling
  enforces it.
- **Accepted-and-unimplemented is a normal, stable state**, not an oversight
  to route around. Documenting a default must not turn it into a kernel
  requirement, and describing the wait for an accepted option as short needs
  an assigned owner and a committed date from the implementing side —
  otherwise it is indefinite.
