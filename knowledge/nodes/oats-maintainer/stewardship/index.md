# Stewardship

How the OATS project ships: judgement only, each concept with an owner and an
update-on-change rule; procedures live in the oats-expert soul's skills.

* [Presentation features reuse one state contract unless divergence is justified](presentation-features-reuse-one-contract.md) - Review new instance-presentation features against the established state and mutation boundaries, requiring a reason for divergence so display choices do not acquire identity, policy or lifecycle meaning.
* [Coordination policy lives in capabilities, not in the kernel or oats.core](coordination-policy-lives-in-capabilities.md) - Review keeps team coordination policy out of neutral lifecycle mechanisms; OATS delegates finished-worker retirement to experts and lane maintainers without a fresh human request, through its composed capabilities.
* [How the OATS project ships and reviews](review-protocol.md) - Maintainer review binds verdicts to content and recorded decisions, preserves same-area integration evidence inside merge batches, requires timely, safely obtained verification, uses fresh and second readers, aims release-prep second reads at hand-written claims, and judges tests against requirements rather than implementations.
* [One release lane does the final review, merge and tags; project lanes are defined by their own maintainers](release-lane-and-project-lanes.md) - One release lane owns final review, merge and tags; maintainers define project lanes without sign-off, launch, review and name one second reader inside them, route package follow-ups by the lane map rather than by who opened the PR, record changed lane practice on the map in the same session, and hand approved heads to the release lane.
* [Release judgement for the tag-driven lane](release-traps.md) - Release judgment distinguishes publication from artifact availability, rehearses released-state upgrades, changed macOS tests and newly taught skill commands before tags, contains failed-tag repairs, gates a package soul's new key on an installed accepting kernel, and coordinates source, tag, mirror, every form of version pin and the framework release that carries them.
* [Cross-workstream delivery: freeze the contract first, adopt then adapt, prove the merge](multi-workstream-delivery.md) - Freeze shared contracts before implementation, adopt then adapt sibling suites, and prove merge fidelity; ship-together sets need whole-set evidence before the first merge or an explicit release hold, and a paused shared-package contract stage is reverted before release.
